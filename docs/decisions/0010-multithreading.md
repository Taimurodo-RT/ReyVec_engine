# 0010. Многопоточность: как движок делит работу между ядрами

Дата: 2026-11-01. Статус: принято как направление (просьба Романа записать, чтобы не потерять нить). Работа по этому решению начинается на этапе 5; отдельные пункты могут прийти раньше, если их потребует замер.

## Главная идея

Потоки не делят одни и те же данные посреди кадра. Они передают друг другу **готовые снимки**: один поток закончил и отдал результат, другой его читает. Тогда почти не нужны блокировки и ожидания, а значит нет главной беды многопоточности: потоки не ждут друг друга и не портят данные друг другу.

## Как сейчас (этап 3)

- Процессор и видеокарта уже работают одновременно: пока видеокарта рисует кадр N, процессор готовит кадр N+1. У каждого кадра в работе свои буферы (`slot`), поэтому ждать не нужно.
- Видеокарта внутри сама работает в тысячи потоков.
- На процессоре кадр готовит один поток. Замер стресс-теста (10 000 фигур): 0,7–0,95 мс на Ryzen 9 9900X3D. Пока этого хватает.
- Тяжёлая разовая работа (чтение SVG, нарезка новой фигуры, буквы атласа) идёт в потоке кадра и может дать рывок: пункты 36, 39 и 42 в `docs/vector-bottlenecks.md`.

## Как будет

1. **Логика игры на `bevy_ecs` (этап 5).** Его планировщик сам раскладывает системы (физика, ИИ, анимация, звук) по ядрам. Каждая система заранее объявляет, какие данные читает и какие пишет. Две системы, которые пишут одно и то же, одновременно не запускаются; системы, которые только читают, идут параллельно.
2. **Логика и рисование развязаны.** Логика идёт с фиксированным шагом 60 раз в секунду (решение 0004) и в конце шага выдаёт снимок того, что нужно нарисовать. Рисование берёт два последних снимка и сглаживает движение между ними. Рисование не ждёт логику, логика не ждёт рисование. На мониторе 144 Гц кадры рисуются чаще шагов логики, и движение всё равно плавное.
3. **Фоновые потоки для тяжёлой разовой работы.** Чтение SVG и файлов Motif, нарезка фигур на треугольники, буквы для атласа, подгрузка соседних комнат. Кадр забирает готовый результат, когда он есть, и никогда его не ждёт. Пока фигура не готова, кадр рисует без неё (или с её грубой версией).
4. **Подготовка кадра в несколько потоков — только по замеру.** Раскладку векторного кадра и запись команд для видеокарты можно делить между ядрами. Делаем это, только если замер покажет, что один поток не успевает (см. цели ниже).

## Цели и как их проверять

- **Кадр не ждёт фоновую работу.** Проверка: загрузка большого SVG или новой комнаты посреди игры не даёт всплеска на графике времени кадра. Рывком считаем кадр дольше полутора средних.
- **Подготовка кадра на процессоре** (без логики игры) до 1 мс при 10 000 фигур на эталонном ПК. Если перестанет укладываться — включаем пункт 4.
- **Ядра.** Пул фоновых потоков: число ядер минус одно (одно остаётся потоку кадра). Движок должен работать и на 4 ядрах (уровень RTX 3060-ПК), просто фоновая работа идёт медленнее.
- **Видно в Tracy.** Каждый поток подписан, его работа видна зонами; по Tracy проверяем, что потоки не ждут друг друга.
- **Без гонок данных.** Rust не даёт двум потокам одновременно менять одни данные без явной синхронизации; общие данные между потоками передаются только снимками и очередями.

## Чего не делаем

- Не делим один кадр видеокарты между несколькими очередями видеокарты, пока замер не покажет пользу (решение 0006: одна очередь).
- Не делаем свою систему задач: используем планировщик `bevy_ecs` и пул потоков, который идёт с ним.
